Before build · canvas changes · no APK

The canvas was found — then something else took it away

You said some canvases load and some never do, that the Canvas check showed a canvas was found while nothing played anywhere (Spotify included), and that the Spotlight cards stayed still. Those three symptoms turned out to have five separate causes in the canvas pipeline. All of them are fixed on disk and the whole change compiles (:app:compileFossReleaseKotlin ✓, 3 Kotlin modules recompiled, BUILD SUCCESSFUL). No APK was built — this page is the preview.

Short version: the check was telling the truth about the moment it ran, and then a second step — the background probe that verifies the URL — silently threw the clip away and never told the report. Meanwhile real failures (a rate limit, an expired token, a provider that could not be asked yet) were being stored as “this song has no canvas” for the rest of the session. That is why it looked random per song. Below is each cause, the evidence, and what changed.

1Spotify canvas could never answer (429)

Spotify Canvas style: nothing, for every song. Canvas check: Spotify “nothing” or “lookup failed”.

The canvases endpoint lives on spclient.wg.spotify.com, and both that host and api.spotify.com turn away a request that carries only a bearer token — they want the web player's second header, Client-Token. The session object already knew how to mint one (clientToken()), but nothing ever called it: it was dead code. Worse, the canvas path asked with the library token, which is minted by replaying /api/token with a computed TOTP — exactly the token those two hosts refuse with 429. The 429 was swallowed inside the provider, so it looked like “Spotify has no canvas for this song”.

2“Canvas check says it was checked — but nothing shows it”

The check row read “shown from Tidal / URL checked — plays”, yet no surface ever drew a frame.

Two steps happen to a canvas: the lookup accepts a clip, and then the preloader probes the URL to see whether it really serves video. The old probe treated any non-2xx HEAD answer as “will not play” — including 403 from a CDN that dislikes the client, 405 from a host that refuses HEAD, 429 and every 5xx. A perfectly good canvas was dropped from the cache there, and because the drop happened outside the report, the check kept saying a canvas was shown. The verdict it wrote was also trusted for 30 minutes, so one bad probe refused that clip on every surface for half an hour.

3Some songs were written off for the whole session

A song shows a canvas on one play and never again; or other songs have one while this one “never does”.

Every provider — Tidal, BetterLyrics, Apple — swallowed its own failures into null. The resolver has a deliberate distinction between “a provider answered, and it had nothing” and “a provider fell over”, but with nothing ever throwing, the second case could not happen. So a lookup that ran while the network was still coming up, while Spotify was not connected yet, or while a provider was rate-limiting was recorded as “this song has no canvas” — for the entire session, and the player's retry gave up on it. That is the randomness: it depended on what the first lookup of that song happened to hit.

4Apple Music: dead credential + album canvases always refused

Apple-sourced canvases never appear; the check shows Apple as “wrong song” or “nothing”.

Two independent bugs. (a) The Apple token had no timeouts, was cached forever (Apple's live about an hour), and when the scrape failed it fell back to a hardcoded JWT that expired in June 2026 — so Apple was asked with a dead credential and every 401 read as “this song has no canvas”. (b) Album-level motion artwork is named after the album, and the check compared it to the song title — so the album lookup was refused as the wrong song, always. That whole provider path could never paint anything.

5The prefetch and the screen were asking different questions

Spotlight/next-track canvases ready for one song, still artwork for the one that actually plays.

The service that warms canvases in the background passed only the first artist (“Pritam”), while the player, the Spotlight card and the Apple Music design pass the full credit (“Pritam, Arijit Singh & Amitabh Bhattacharya”). Different query → different provider results → a warmed answer that the screen never asks for. Both now build the artist string the same way. The Spotify provider also stopped handing back another track's canvas when the requested track was not in the response — a “matched” Spotify clip is now this song's.

How to read the Canvas check now

LineMeans
matched / accepted, unjudgedThat provider's clip was usable at that moment (belongs to this song / no names to judge).
nothingThe provider was asked and had nothing. If all of them say this, the song is remembered as canvas-less for 15 minutes — then asked again.
lookup failedThe provider could not answer (offline, 429, expired token, not connected). The song is not written off — a later attempt can still find a canvas.
will not playThe URL was refused — by the background probe or by the actual decoder. Trusted for 5 minutes, then re-tried.
wrong songA clip came back that belongs to something else (cover, remix, another track). Refused; the other providers keep going.
Summary rowSays shown from … only while a clip is actually there. If the probe takes it away, the row flips to nothing shown and a Probe: will not play line is added.
