1“Jay” username flash for ~2 s on app open

Opening the app showed a personal name in the home greeting for a couple of seconds, then swapped to your real name.

The home header had a hardcoded developer name as its last-resort fallback, and the ViewModel starts the account name as “Guest” while the real name is fetched over the network. So the fallback chain landed on the hardcoded name every cold start until the network answered. Now the greeting is seeded instantly from the account name saved at login, the hardcoded name is gone, and a failed lookup can no longer downgrade a saved name to “Guest”.

After

2Lyrics ignored the priority list

Reordering providers in Settings → Lyrics priority had no effect; the default order kept winning.

Two separators have shipped over time: the priority screen writes commas, but the old SimpMusic migration wrote semicolons. The registry only split on the comma, so a semicolon-joined order parsed to a single unknown token, got filtered away, and the resolver silently fell back to the default order. The migration also failed to actually remove SimpMusic from comma-joined strings. Now both sides accept both separators and normalise to the canonical comma.

Before
LyricsProviderRegistry.ktorderString.split(",")  .filter { it in providerNames }// "A;B;C" → 1 token → dropped → defaults
After
LyricsProviderRegistry.ktorderString.split(';', ',')  .mapNotNull { byLowercase[it] }// both formats honoured, case-insensitive
LyricsProviderRegistry.kt MainActivity.kt · migration normalises to “,”

3Spotify lyrics stopped loading after a while

Spotify lyrics worked right after signing in, then answered “nothing found” for the rest of the session.

The provider read the raw library token, which lapses shortly after login — and nothing re-mints it while music plays. The canvas resolver already knew this (its comment describes the exact failure) but the fix lived privately there. The resolution (expiry check → fresh web-player re-mint → fallback) is now shared via SpotifySession.freshAccessToken(), used by both the lyrics provider and the canvas resolver — so they can never disagree again.

Before
SpotifyLyricsProvider.ktval token = Spotify.accessToken    ?: return failure("Not signed in")// stale token ⇒ 401/429 ⇒ "no lyrics"
After
SpotifyLyricsProvider.ktval token = SpotifySession    .freshAccessToken(context)// expiry-checked + re-minted, shared
SpotifyLyricsProvider.kt SpotifySession.kt · new freshAccessToken() CanvasResolver.kt · delegates to it

4Lyrics sometimes never followed the song

Some songs showed lyrics that never moved (raw <00:12.34> tags visible), and occasionally the view opened parked at the end of the song during its first seconds.

Two separate causes. (a) The lyrics pipeline used a regex hint ([mm:ss) to decide whether to parse — but word-timed payloads (Spotify/Musixmatch rich format) carry no line stamps at all, so they were dumped into the plain-text fallback with their tags still in the text. The real parser now makes that call, exactly like every other lyrics surface. (b) The full-screen view’s scroll target is rememberSaveable, so a restored index from the previous song could survive into the next one when the lyrics object was identical — it now resets per media id, so every song starts from its beginning.

Before
LyricsViewModel.ktval isLrc = timestampRegex…if (isLrc) parseLyrics(lyrics) else emptyList()// word-timed lyrics ⇒ fallback ⇒ frozenExperimentalLyrics.ktLaunchedEffect(lyrics, lines) { reset }
After
LyricsViewModel.ktval parsedLines = LyricsUtils.parseLyrics(lyrics)// parser decides — word-timed now followsExperimentalLyrics.ktLaunchedEffect(lyrics, lines, mediaMetadata?.id)// always start at the top of a new song
LyricsViewModel.kt ExperimentalLyrics.kt

5Canvases that used to load stopped loading

A song’s animated canvas sometimes never appeared again — even after changing the Canvas style in Settings.

The resolver remembers “this song has no canvas” to avoid re-asking every provider — but that memory survived a style change, while the answer absolutely depends on the style (a Spotify-only miss can be a hit under Glossy, especially after fix #3). The per-song miss memory is now cleared whenever the style is invalidated, so changing style re-asks instead of staying silent for the rest of the session.

Before
CanvasResolver.ktfun invalidateStyle() {    cachedStyle = null}// old "no canvas" misses kept forever
After
CanvasResolver.ktfun invalidateStyle() {    cachedStyle = null    definitiveMisses.clear()}// style change ⇒ providers asked again
